# 架构：一条可核对的链路

```
                         ┌──────────────────────────────┐
   KIMORE 骨架 CSV ──▶   │  ① 评估内核（MCP Server）      │
   （25 关节 × 30 Hz）    │  5 个工具 / 统一信封 / 溯源    │
                         └──────────────┬───────────────┘
                                        │ SSE / Streamable HTTP
                         ┌──────────────▼───────────────┐
   Nexent ◀────────────▶ │  ② 智能体编排                 │
   （模型 / 记忆 / 评测）  │  4 角色：受理 → 评估 → 解释 → 方案 │
                         └──────────────┬───────────────┘
                                        │ 读「能说什么」
                         ┌──────────────▼───────────────┐
                         │  ③ 本体 + SHACL               │
                         │  什么特征能下什么结论，硬校验    │
                         └──────────────┬───────────────┘
                                        │ 治疗师改判
                         ┌──────────────▼───────────────┐
                         │  ④ 进化闭环                   │
                         │  修正 → 条目化 → 评测 → 灰度    │
                         └──────────────────────────────┘
```

## 每一层解决什么问题

### ① 评估内核（`mcp_server/`）

对外只暴露 5 个工具，参数和返回都是死契约：

| 工具 | 干什么 | 关键约束 |
| :-- | :-- | :-- |
| `list_samples` | 列出可用记录 | 模型不知道该用哪个 ID 时先调它 |
| `assess_exercise` | 算 17 个特征 + 与参照比 | `predicted_score` 恒为 null（未验证不预测） |
| `query_criteria` | 拿判定口径 | 口径是数据，不是提示词里写死的话术 |
| `explain_deviation` | 某处偏离的证据链 | 返回 `evidence[]`，**不是** `deviations[]` |
| `plan_session` | 多条记录横向对照 | 只返回横截面 8 个字段，1–5 条，不可重复 |

统一信封：

```json
{
  "schema_version": "0.1.0",
  "request_id": "…",
  "status": "ok | partial | rejected | error",
  "data": { },
  "warnings": [],
  "error": { "code": "SAMPLE_NOT_FOUND", "retryable": false },
  "provenance": { "source_type": "recorded_kinect", "…": "…" }
}
```

**状态码与业务错误分开**：MCP 层永远返回正常响应，错误放在 `error.code` 里。
这样模型不会因为一次「样本不存在」就崩掉整轮对话，而是能按话术告诉用户换一条。

### ② 智能体编排（Nexent）

四个角色，但**不是四份提示词**，而是一条流程上的四个停靠点：

```
受理（收敛成合法 sample_id） → 评估（拉数） → 解释（拉口径 + 拉证据） → 方案（可做/不可做）
```

编排靠三样东西撑起来，缺一个就会退化：

1. **工具白名单**：只给 5 个工具，混进来的旧工具会让模型乱调。
2. **技能（Skill）**：把「怎么写」从提示词里拿出来，版本化。S2 已经是 v3。
3. **提示词硬规则**：四条不变量——数字只来自工具、只对 `deviations` 说偏离、只有 `*_peak` 报帧号、重复次数三档话术。

### ③ 本体（`ontology/`）

提示词是软约束，模型可能忘；SHACL 是硬校验，跑不过就是跑不过。

典型约束：

- 特征缺 `hasSourceLine`（脚本行号）→ 这条特征不许进结论。
- `unit=degree` 且 `verticalReferenceIndependent=false` → 必须有 `signConvention`（否则正负号没人说得清）。
- `Assessment.observedLabelPresent=false`（这条记录没有临床评分）→ 不得挂任何 `Deviation`。
- `Plan` 的文本出现「诊断 / 处方 / 治愈 / 确诊」→ 违规。

校验一次：

```bash
python tools/validate_ontology.py            # good 应 conforms=True，bad 应 7 条命中
```

### ④ 进化闭环

一次治疗师改判，走完这五步才算「吸收」：

```
改判 → 结构化修正条目 → 数据侧核对（特征支持不支持） → 评测集回归（一致率） → 灰度
```

修正条目是结构化的（原结论 / 治疗师判断 / 数据侧核对 / 建议本体变更 / 影响面 / 下一步），
所以它可以被 diff、被评审、被回滚——**这是「可进化」和「凭感觉改提示词」的区别**。

## 为什么这么切

| 选择 | 否决的方案 | 理由 |
| :-- | :-- | :-- |
| 特征与规则放服务端 | 全塞进提示词 | 提示词改一次要重跑全部评测，且无法溯源 |
| 判定口径走 `query_criteria` | 写在系统提示词 | 口径要能被引用、被版本化、被非技术人员校对 |
| 本体做硬约束 | 只靠提示词 | 模型会忘，SHACL 不会 |
| 不做分数预测 | 用 cTS 训回归 | 只有三层汇总分，没分项；预测出来也解释不了 |
