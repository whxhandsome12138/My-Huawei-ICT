# 用途

系统的进化不是"模型自己学"，而是**治疗师改一次、系统记住一条**。

这条流程把一句口头修正（"这个不算代偿，他本身就有侧弯"）变成可评审、可回归、可版本化的结构化条目。

# 什么时候用

- 治疗师说"这个判断不对""其实不是这个原因"
- 治疗师对某个偏离点的解读与系统不一致
- 治疗师提出新的判定条件（例如某个角度阈值该按人群调整）

不适用：治疗师只是补充背景信息、没有推翻任何结论 → 不必走这条流程。

# 步骤

1. **固定被修正的对象**
   问清是哪一条评估、哪一个偏离点。
   取 `assess_exercise(sample_id)` 拿到原始结论，取 `explain_deviation(sample_id, feature_id)` 拿到支撑证据。

2. **记录治疗师判断**
   要让对方说清三件事：**结论错在哪**、**应该是什么**、**依据是什么**。
   依据可以是经验，但要标明"经验判断"，不能伪装成数据。

3. **回查数据是否支持**
   用已有特征验证治疗师的说法：

   - 说法与特征一致 → 标"数据支持"
   - 说法与特征不一致 → 标"数据不支持，待讨论"，并指出冲突的是哪个特征
   - 数据里没有相关特征 → 标"当前特征集无法验证"

   **不要为了让条目好看而跳过第 3 步。**

4. **给出建议的本体变更**
   只说清"建议改什么"，不说"已经改了"：

   - 新增条件（例如"存在既往脊柱侧弯时，该偏离点不单独计为代偿"）
   - 调整阈值（例如某个参照分位从 p25 改为 p10）
   - 补充说明（`notProvided` 增加一项）

5. **评估影响面**
   这条修正会影响哪些样本、哪些结论类型。说得出就写，说不出就写"待回归验证"。

6. **输出条目**
   按下面的模板给结构化结果，并明确下一步：交人工评审 → 改本体 → 回归 → 灰度。

# 输出模板

```
修正条目（候选，未生效）

一、被修正的结论
- sample_id：Es2-…
- 原结论：<系统说了什么>
- 涉及特征：<feature_id>
- 支撑证据：<observed / reference / difference / frame_index>

二、治疗师判断
- 结论错在：<具体哪句话>
- 应为：<正确解读>
- 依据：<经验判断 / 其他检查 / 影像>（标明类型）

三、数据侧核对
- 结论：数据支持 / 数据不支持 / 当前特征无法验证
- 说明：<与哪个特征冲突或一致>

四、建议的本体变更
- 类型：新增条件 / 调整阈值 / 补充说明
- 内容：<一句话规则>
- 影响范围：<受影响的样本或结论类型 / 待回归验证>

五、下一步（尚未执行）
1. 人工评审该条目
2. 合入本体并升版本号
3. 跑回归评测集，比对一致率
4. 小比例灰度后观察分歧率
```

# 硬规则

- **不得**声称"已更新本体""已生效""已加入规则库"。产出永远是候选条目。
- 治疗师的判断与数据冲突时，如实写"数据不支持"，不要两边都讨好。
- 不要替治疗师补依据。他说是经验，就写经验。
- 一条修正只针对一个特征或一个规则，不要打包多条，否则无法回归。

# 失败处理

| 情况 | 做法 |
|---|---|
| 治疗师说不清依据 | 先按"经验判断"记录，标注待补充 |
| 拿不到原始评估 | 先跑一次评估再记录，不要凭记忆写 |
| 修正涉及诊断/处方 | 记下来，但注明"超出系统范围，仅作背景" |

# 与文档的对应

这条流程对应开发文档「可进化闭环」一章：一次修正 → 本体候选版本 → 评测集回归 → 灰度观察。条目里第 4、5 段就是给文档用的原始素材。
